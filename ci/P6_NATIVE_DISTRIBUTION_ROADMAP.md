## B. Current and proposed architecture

**R, current:** React/BlockNote production assets are served by FastAPI from the
GUI-owned backend. Qt WebEngine displays its authenticated loopback origin.
SQLite and raster assets remain in a private Profile. The production entrypoint
requires Flatpak identity, /app layout, no shared host network/broad filesystem
access and a specific sandbox-aware QtWebEngineProcess. The older source installer
is a separate Firefox deployment, not an existing native installer.

**P, proposed:**

```text
Git source/tag + reviewed locks
  -> CI builds frontend and assembles full native archive + wheelhouse + notices
  -> owner signs reviewed archive/checksums and authorizes GitHub publication
  -> user verifies authentic archive BEFORE executing its install.sh/update.sh
  -> shared per-user installation engine
       -> immutable versioned application directory + final-location private venv
       -> verified synthetic startup, then atomic current-release selection
  -> desktop entry -> stable native bootstrap -> existing Qt window
       -> owned authenticated FastAPI child -> existing frontend
       -> stable native user profile -> SQLite/assets + workspace-specific Qt storage
```

One source tree and full releases are simpler than committed `update x.x` folders.
Do not maintain a growing sequence of file-copy patches or ask users to clone Git.
A newer full package replaces binaries as one version; skipped-version updates
work if its declared schema migration range includes the current database. Existing
migration accepts source schemas 3/4/5 and preserves content while reaching 5.
Future unsupported jumps must refuse and explain the supported migration path.
No implementation or guarantee for future schemas is invented here.

## E. Security model and required owner decisions

| Layer | Retained or changed | Plain-language consequence |
| --- | --- | --- |
| Private venv | Keeps dependency versions separate from system Python | It does **not** restrict filesystem, network or process privileges. |
| Application protections | Keep authentication/Host-Origin/CSP, navigation/resource/download restrictions, no JS filesystem bridge, image/path/database protections and instance/child ownership | These protect application operations and backend access; they are not a whole-process sandbox. |
| WebEngine renderer | Must retain actual Chromium namespace/seccomp isolation, using coherent upstream native binaries | A compromised page should remain restricted by the renderer sandbox. Native sandbox feasibility is presently unproved. |
| Whole Qt/Python application | Flatpak filesystem/network/bus confinement is lost | GUI/backend and loaded native code can use the user's normal file/network privileges. A compromise there can reach other readable user files and external services. Mode0700 protects other users, not same-user malware. |

**P:** ordinary-user desktop model, not a replacement bubblewrap/portal platform.
No root GUI, global pip, new local daemon, web browser substitute or automatic
update server. Native dialogs remain explicit user choices, but a dialog is no
longer a sandbox-enforced grant for the rest of the application.

The backend remains prebound to 127.0.0.1, not 0.0.0.0/::, with its inherited socket
and fresh per-launch credential supplied only through a pipe. **Host loopback is
shared**, so other applications can connect; require a valid token for every route,
exact Host/Origin, no WebSocket access and revocation after death. Test attacks from
another ordinary host process and another web origin. Never adopt a listener merely
because it answers health. Preserve the recorded port; fail visibly if occupied,
without silently changing origin and losing browser state. No claim of protection
from privileged or malicious same-UID code is made. Existing no-external-resource
policies limit normal traffic but cannot confine a compromised native process.

Owner decisions, separated from implementation mechanics:

1. The owner has accepted the ordinary-user whole-application filesystem/network
   privilege tradeoff. This does not waive the required renderer sandbox.
2. N1 implementation is already authorized; the issued owner-host renderer probe
   awaits its morning result. Further development is on hold pending review; any
   AppArmor/system integration remains a separate explicit decision.
3. MIT is selected for the original code. Copyright-holder attribution, branding
   rights, the dependency/source/notice arrangement and authentic signing identity
   remain separate matters; no license-file change is authorized by this update.
4. Later approve commit/push/CI/publication and any coexistence/migration of actual
   user data. No such authority is inferred from this roadmap.

## F. Installation, update and data-safety design

**P, one engine:** extract safe generic installer helpers into
`desktop/install_engine.py` while preserving `desktop/install.py`'s legacy source
entry and its tests. New tiny wrappers call install/update/uninstall operations in
that engine. The native launcher delegates runtime ownership to the existing Qt
shell/backend rather than the Firefox supervisor. Keep dependencies stdlib until
the private environment exists. Do not import the complete CI release framework.

Release archive contains built application/dist, runtime wheelhouse and hash lock,
manifest/provenance, icon/notices/source instructions and these wrappers/engine.
Users do not run npm, Git, a compiler or source build. Prefer offline installation
of Python wheels from this authenticated archive using pip's
[hash-required, binary-only mechanism](https://pip.pypa.io/en/stable/topics/secure-installs/)
with no index, including hashes for every transitive runtime dependency. OS packages
are separate trusted Ubuntu prerequisites: interpreter/venv, GnuPG verification,
and the measured graphics/native-library closure. Print exact missing packages and
stop. Any privileged apt step is separately user-executed/approved; never invoke
sudo automatically or launch the GUI as root. First install may need network for
Ubuntu packages; application use is offline after successful installation.

### Authenticity before executing the downloaded installer

A checksum or public key beside an untrusted script cannot authenticate it.
The owner must establish an authentic public signing fingerprint through a
previously trusted key or an independently trusted channel. Validate the detached
archive signature with Ubuntu GnuPG and that expected full fingerprint **before
extracting/executing any downloaded wrapper**. Merely seeing “Good signature” from
a newly downloaded arbitrary key is insufficient. First-use trust remains an owner
release decision; no real production key is identified or generated here.

Sign exact final archive bytes and the checksum/provenance manifest offline. Keep
one encrypted offline key backup and a short revocation/replacement procedure;
no CI signing service or multi-person ceremony. Future installed updater can reuse
its already trusted verifier/key. Key replacement requires an authenticated
transition or an explicit new trust decision, not a new key inside an update ZIP.
Expiry/revocation/signature and wrong-key tests remain. Integrity verification
must not become an undocumented prohibition on recipients replacing LGPL libraries
in a separately identified modified installation.

### Staging, activation and interruption

1. Verify archive signature/hash, source/version/platform/schema manifest and space
   budget before touching active code or data. Reject downgrade/unexpected identity
   unless an explicit compatible recovery operation is chosen.
2. Safe bounded extraction: reject absolute/parent paths, duplicate entries, special
   files, hardlinks and unapproved links; do not follow destination symlinks. Audit
   every extracted file against the signed inventory. Generated venv symlinks to
   the selected interpreter are distinct from untrusted archive links. No embedded
   database, notes, credentials, logs, caches, keys or test harness.
3. Acquire one installer lock shared with the native launch path and hold the
   instance lock while changing selection. Refuse running GUI/backend; request Saved
   and normal close. Do not kill arbitrary processes or race a new application start.
4. Create new unique final release directory marked incomplete, build its venv there,
   install only locked local wheels, pip check, verify paths/providers, run isolated
   synthetic backend/startup checks. Old current release remains selected throughout.
   Do not rename a populated venv from staging to its final location.
5. Read schema compatibility without initializing the personal DB. Before any
   supported schema-changing first start, obtain a verified stopped-workspace backup
   with the existing domain tool. Updates must not rewrite a real workspace during
   staging or reset the active-workspace pointer. Qt browser-profile formats also
   need compatibility consideration; a database backup alone does not preserve them.
6. Journal prepared state; fsync files/directories; atomically replace validated
   current.json and preserve previous selection. Use a stable launcher/icon/menu so
   routine updates change one active pointer, not multiple program trees. First menu
   registration and engine upgrades need explicit interruption recovery tests too.
7. On failure before activation, old installation is usable; retain a small private
   diagnostic and quarantine incomplete payload. After activation but before successful
   startup, offer explicit recovery to previous code only if data and Qt-profile
   compatibility is verified. Never silently roll back and start incompatible code.
   Resume/refuse a recorded incomplete transaction deterministically; no overwrite
   of active files one by one. Retain current and previous usable releases; cleanup
   of older releases is explicit and separate from data deletion.

**Binary rollback is not database rollback.** Current DB refuses versions >5;
there is no reverse migration. For incompatible data, restore a verified pre-upgrade
backup into a new workspace and activate it deliberately, preserving current data.
Do not promise zero data loss for edits made after that backup. Qt storage can also
be upgraded by Chromium; preserving a previous binary alone cannot guarantee that
it reads a newer browser profile. Keep a stopped-profile checkpoint or restrict
rollback where that compatibility is unproved. A failed install before any real
launch needs no data rollback.

Uninstall removes only exact managed program/menu/launcher paths under lock after
closure and ownership checks. It preserves notes/assets, workspace selection, Qt
profiles, backups and recovery drafts by default. No automatic purge of user data,
other Flatpak installs, legacy Firefox launcher, global libraries or signing keys.

### State and Flatpak-to-native migration

**R:** Profile persists port in desktop.json, named Qt profile “CyrNava”, explicit

### Proposed end-user flow — wrappers/assets do not exist yet

1. Download the versioned Ubuntu26.04-x86_64 release archive, detached signature and
